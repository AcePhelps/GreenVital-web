# Offline Vault Windows Release Infrastructure Handoff

Status: **blocked and unpublished**

The public Offline Vault page must remain in its current `Coming soon` state until every release gate in this document passes. Do not upload the self-signed test build, create a placeholder `release.json`, or point DNS at an unvalidated origin.

## Current state

- `greenvital.app` is served by GitHub Pages from the repository root on the `main` branch.
- GitHub Pages has an approved certificate for `greenvital.app` and `www.greenvital.app`, but its `Enforce HTTPS` setting is currently off. Both HTTP and HTTPS respond. Enable enforcement before activating a public download release.
- GitHub Pages is appropriate for the product page, but not for the Windows artifacts because the required MSIX/App Installer response headers cannot be controlled reliably there.
- `downloads.greenvital.app` does not currently resolve.
- The product page requests `https://downloads.greenvital.app/offline-vault/windows/release.json` and keeps both Windows controls disabled when DNS, the manifest, or any required manifest field is unavailable or invalid.
- No production-signed or trusted-timestamped Windows bundle exists yet.

## Recommended production origin

Use a private Amazon S3 bucket behind Amazon CloudFront:

1. Keep S3 Block Public Access enabled.
2. Give CloudFront read access through Origin Access Control (OAC), using the recommended `always` signing behavior.
3. Add `downloads.greenvital.app` as the CloudFront alternate domain name.
4. Request an AWS Certificate Manager public certificate for `downloads.greenvital.app` in `us-east-1`, which is the region CloudFront requires for viewer certificates.
5. Set the CloudFront viewer protocol policy to redirect HTTP to HTTPS and use TLS 1.2 or newer.
6. Disable automatic compression for the binary package behavior.

This choice works with the existing Porkbun authoritative DNS and does not require moving the root website or changing its GitHub Pages configuration.

## DNS records in Porkbun

Two DNS changes are required, in this order:

1. Add the ACM certificate-validation CNAME exactly as AWS provides it. Its host and target are generated by ACM and cannot be known before the certificate request.
2. After CloudFront has been created with the validated certificate, add:

| Type | Host | Answer / value | TTL |
| --- | --- | --- | --- |
| CNAME | `downloads` | the assigned CloudFront hostname, such as `d123example.cloudfront.net` | 600 |

Do not add A or AAAA records for `downloads.greenvital.app`. It is a subdomain and should be a CNAME to the assigned CloudFront distribution hostname. Do not publish the CNAME until the distribution is configured and responds correctly on its CloudFront hostname.

## Bucket layout

Keep Windows files under one stable prefix:

```text
offline-vault/windows/
  OfflineVaultCompanion-{version}.msixbundle
  OfflineVaultCompanion.appinstaller
  release.json
```

Future versioned bundles should remain available while any published App Installer feed can still reference them. The App Installer filename and `release.json` URL stay stable; the bundle filename is versioned.

## Required object metadata

Set metadata during upload. S3 preserves `Content-Type` and `Cache-Control`, while S3 and CloudFront supply `Content-Length` from the stored object size.

| Object | Content-Type | Cache-Control |
| --- | --- | --- |
| `OfflineVaultCompanion-{version}.msixbundle` | `application/msixbundle` | `public, max-age=31536000, immutable` |
| `OfflineVaultCompanion.appinstaller` | `application/appinstaller` | `public, max-age=300, must-revalidate` |
| `release.json` | `application/json; charset=utf-8` | `public, max-age=60, must-revalidate` |

Every `GET` and `HEAD` response must include a valid `Content-Length`. A range request such as `Range: bytes=0-0` against the bundle must return HTTP 206 with valid `Accept-Ranges: bytes`, `Content-Range`, and `Content-Length` headers. Do not redirect any of the three public URLs.

## CORS and HTTPS

The product page reads `release.json` across origins. Attach a custom CloudFront response headers policy to the three Windows cache behaviors with this CORS configuration. A dedicated bucket may instead use an equivalent bucket-wide S3 CORS policy.

- Allowed origin: `https://greenvital.app`
- Allowed methods: `GET`, `HEAD`
- Allowed headers: `Range`
- Exposed headers: `Accept-Ranges`, `Content-Length`, `Content-Range`, `ETag`
- CORS max age: 300 seconds

CloudFront should add `Strict-Transport-Security` only after HTTPS is confirmed stable. All public checks must use `https://downloads.greenvital.app`; do not accept HTTP, a certificate warning, an S3 URL, or a CloudFront hostname in `release.json`.

## CloudFront cache behaviors

Create explicit behaviors under `/offline-vault/windows/`:

| Path pattern | Viewer methods | TTL policy |
| --- | --- | --- |
| `/offline-vault/windows/*.msixbundle` | GET, HEAD | honor the one-year immutable object policy |
| `/offline-vault/windows/*.appinstaller` | GET, HEAD | 0 to 300 seconds |
| `/offline-vault/windows/release.json` | GET, HEAD | 0 to 60 seconds |

When using the CloudFront response headers policy, set origin override so the CORS result is stable at the edge. If S3 CORS is used instead, forward and include the `Origin` header in the cache key. Preserve viewer `Range` requests so bundle downloads support byte ranges. Do not attach signed URL or cookie requirements because Windows App Installer must fetch these public release files directly.

## `release.json` contract

Publish exactly one JSON object with these fields. Generate every value from the final signed bundle, not from a development or self-signed build.

| Field | Required value |
| --- | --- |
| `version` | non-empty release version string used in the bundle filename |
| `minimumWindowsVersion` | approved minimum Windows version string |
| `architectures` | unique array containing `x64`, `arm64`, or both |
| `msixBundleUrl` | absolute HTTPS URL on `downloads.greenvital.app` ending in `OfflineVaultCompanion-{version}.msixbundle` |
| `appInstallerUrl` | `https://downloads.greenvital.app/offline-vault/windows/OfflineVaultCompanion.appinstaller` |
| `sha256` | 64-character lowercase SHA-256 of the final bundle |
| `sizeBytes` | exact positive integer byte size of the final bundle |
| `releasedAt` | ISO-8601 UTC timestamp ending in `Z` |

## Release gates and publication order

1. Obtain a trusted production code-signing certificate and protect its private key in the signing provider or a managed signing service.
2. Sign the final x64 and ARM64 bundle with the production identity and apply a trusted RFC 3161 timestamp.
3. Verify the package signature, publisher identity, version, architectures, clean-machine installation, update behavior, and iPhone pairing flow.
4. Compute SHA-256 and exact byte size from the final signed `.msixbundle`.
5. Upload the versioned `.msixbundle` first with its final MIME type and immutable cache metadata.
6. Upload `OfflineVaultCompanion.appinstaller` second. It must reference the exact HTTPS bundle URL and match the package identity, publisher, and version.
7. Validate DNS, TLS, no redirects, MIME types, `Content-Length` on GET and HEAD, byte-range behavior, CORS, and cache headers for both files.
8. Enable `Enforce HTTPS` for the existing GitHub Pages site and verify HTTP redirects to HTTPS.
9. Build `release.json` from the already-published artifacts and validate it locally.
10. Upload `release.json` **last**. This is the action that allows the product page to enable the Windows controls.
11. Invalidate only `release.json` and `OfflineVaultCompanion.appinstaller` in CloudFront, then run the live validator and confirm the GreenVital product page enables the correct links.

If a release must be withdrawn, remove or replace `release.json` with a non-available response and invalidate it first. The page will return to its static disabled state. Preserve the underlying versioned bundle while investigating clients that may already have received the update feed.

## Repository preflight validator

Validate a candidate manifest without making network changes:

```bash
node scripts/validate-offline-vault-windows-release.mjs /absolute/path/to/release.json
```

After `release.json` is intentionally published last, validate the public origin and all response headers:

```bash
node scripts/validate-offline-vault-windows-release.mjs --live
```

The live check fails closed on DNS errors, redirects, incorrect origins or filenames, schema errors, MIME errors, missing lengths, bad CORS, unsuitable cache policies, or broken range requests.
